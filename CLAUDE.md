# Umbraco Analytics UI

Shared backoffice analytics components (Lit + UUI) consumed by Engage, Commerce and Umbraco AI. Shipped once per site via NuGet RCL + backoffice import map. The same source also builds `@umbraco/analytics-ui-core` for pages outside the backoffice.

## Rules

- Components draw only. No API calls, no product contexts (`ENGAGE_*`, `UC_*`, `UAI_*`), no product types in the public API.
- Never expose Chart.js types or config in our public API (`src/index.ts`, `api/analytics-ui.api.md`, `api/analytics-ui-core.api.md`). Wrap it in our own options types.
- Chart.js is bundled into its own entry, `src/external/chart.js/index.ts` (re-exported as is), mapped as `@umbraco/analytics-ui/external/chart.js` for products. In the Umbraco build, shared code reaches it through `#platform/chart`, which resolves to that bare specifier (aliased to the source for tests, tsc and Storybook; external in the build), never `"chart.js"` or a relative path (lint enforced; `check:size` checks the bundle): the CMS cache-busts import map URLs, so a relative import loads a second copy. Only `@umbraco-cms/*` is external. The core build keeps `lit`, `@umbraco-ui/uui` and `chart.js` external: `lit` and UUI are peers, `chart.js` is a dependency of `@umbraco/analytics-ui-core`. Chart.js's major is part of our compatibility promise: a Chart.js major only at a CMS major.
- Register per chart, never globally: no `Chart.defaults` changes and no global `Chart.register` of plugins (pass them in the chart's `plugins`). Our chart sets everything it relies on per chart; `time-series-chart.isolation.test.ts` guards that.
- Colours via UUI CSS custom properties only. Must work in light and dark mode.
- Number/date formatting via `Intl` with the backoffice user's culture (the core takes it from `lang`). Currency and units come from the consumer.
- Every user-facing string (text, `aria-*`, `title`, `placeholder`, visually hidden text, announced joins and separators) goes through a localization key: reuse an Umbraco key for generic words (`general_*`, `buttons_*`), else add a `uauiAnalytics_*` key to `Client/src/lang/en.ts`. Keys are whole literals, never built from parts. `src/lang/localization.*.test.ts` fails on untranslated text, missing or unused keys.
- Everything exported from `Client/src/index.ts` is public API, including element names, attributes and event names.
- Minor versions must never break: one version is shared by every product on a site. Run `npm run check:api`; a changed `api/*.api.md` report (`analytics-ui.api.md` or `analytics-ui-core.api.md`) needs explicit reviewer sign-off.
- Obsolete before removal: `@deprecated Use X instead. Will be removed in vN.0.0` (current major + 2).
- Package major = CMS major. Keep `version.json`, `Client/package.json` and the `Umbraco.Cms.*` range in `Directory.Packages.props` in sync.
- Prerelease suffixes are dot-separated: `-alpha.N`, `-beta.N`, `-rc.N`.
- Add a component only when at least two products need it.
- Componentize (single responsibility). Build each distinct UI piece (cell, pager, tooltip, legend, toolbar parts) as its own small element, internal under `src/internal/` or the component's `internal/` folder unless there's a reason to make it public. Composite elements compose them rather than rendering everything inline. Making an internal element public later is non-breaking; the reverse isn't.
- Reusing a component for a new purpose: you MUST re-evaluate its name (and folder) so it fits every use, e.g. `uaui-share-bar` became `uaui-meter-bar` in `src/internal/` once the progress cell used it. Internal elements rename freely; a public one needs the deprecate-then-remove route.
- Consistency with UUI is a goal. Where UUI already has the pattern (property/attribute names, events and their cancelability, states like selectable/selected/disabled, focus, hover and selection visuals, sizes), mirror it. Read the UUI source in node_modules/@umbraco-ui/uui first. Deviate only to close a gap UUI has (e.g. accessibility) and log the deviation in the plan's DECISION-LOG.md. Don't import from `@umbraco-ui/uui/internal/*`: it isn't re-exported by the backoffice, so it would bundle a second UUI copy.
- Versioning: package major = CMS major (19.x for CMS 19); minor and patch are this package's own. Only breaking changes at a CMS major, since one version is shared by every product on a site.
- Branching: `v{major}/main` = latest release on that major (code only via release/hotfix merges); `v{major}/dev` = integration branch; work on `v{major}/topic/<name>` (any unit of work: feature, fix, experiment) and PR into `v{major}/dev`. Every feature gets its own new topic branch, forked from the latest `v{major}/dev`, checked out in its own git worktree (separate working folder); never build a feature on `v{major}/dev`, `v{major}/main` or another feature's topic branch. Releases: `release/{semver}` off `v{major}/dev`, tag `release-{version}` on it, merge to `v{major}/main` after the build succeeds. Hotfixes: `hotfix/{semver}` off `v{major}/main`. Only `v19` exists for now. Until the first release (user decision 02-11-2026), `v19/main` may be fast-forwarded to `v19/dev` to publish the Storybook docs; after the first release, release/hotfix merges only again.
- Component folder layout follows UUI: `<name>.element.ts`, `<name>.story.ts`, `<name>.test.ts`, `index.ts`. Element prefix `uaui-`.
- Every component needs a story covering each state and a test that includes `expect(await axeRun(el)).toHaveNoViolations()`.
- Platform seam (lint enforced): shared code imports Lit, UUI, Chart.js, the base element (`UauiLitElement`), context helpers and the date range opener only through `#platform/*` (`#platform/lit`, `uui`, `chart`, `base-element`, `context`, `date-range-opener`, ...). Only `src/platform/` may import `lit`, `@umbraco-ui/uui`, `chart.js` or `@umbraco-cms/*` directly. Exceptions (see `eslint.config.mjs`): `src/examples/**` and `src/docs/*.mdx` (they show product code); UUI theme CSS; `src/external/chart.js/index.ts` and `look.ts` may import `chart.js` directly, and `look.test.ts` may use the bare `@umbraco/analytics-ui/external/chart.js` specifier. Only `src/platform/` may reach `src/platform/umbraco/` or `src/platform/core/` by relative path, except specs and `src/internal/test/**`, which may reach `src/platform/core/` but not `src/platform/umbraco/`. Stories are not exempt from the Lit/UUI/Chart.js rule; they may use relative imports into `src/platform/umbraco/` (Storybook runs the Umbraco build). Lint cannot catch every backoffice import: `tsconfig.core.json` and the core project's throwing `@umbraco-cms/*` stub catch the rest. Never add a backoffice import outside `src/platform/umbraco/`: the core must load with no `@umbraco-cms/*`. A new swap point needs a file in each of `src/platform/umbraco/` and `src/platform/core/` plus a `package.json` `imports` entry (always `src/platform/umbraco/`); add it to `platformBuildAlias` (`Client/vite.config.ts`) only when it re-exports an external specifier. Everything else follows by wildcard: `coreTestAlias` and the `#platform/*` `paths` in `tsconfig.core.json`, `tsconfig.core-api.json` and `tsconfig.core-api-extractor.json` map any name to `src/platform/core/`.
- Two builds from one source: the Umbraco build (`vite.config.ts`, `@umbraco/analytics-ui`) and the core build (`vite.config.core.ts`, `@umbraco/analytics-ui-core`, one file at `dist/core`). The core's peers are `lit` and `@umbraco-ui/uui`; it has the same version as the main package (both packed from `version.json`). Core has its own small translations, table context and 6 fallback icons (alert, search, delete, calendar, navigation-left, navigation-right); each shipped icon name is a promise, so add one only when a component draws it. Core bundle budget: 56 KB gzip (`check:size`).
- Tests: two Vitest projects. `core` (default, runs against the core swap points, `@umbraco-cms/*` aliased to a throwing stub) and `umbraco` (backoffice integration, `src/examples/**` and the smoke set). Specs in `core` must not import `src/platform/umbraco/`. Put a spec in `umbraco` only if it needs the backoffice.
- Changelog: any change a product team would notice adds a line under `## [Unreleased]` in `CHANGELOG.md`, in the same PR. That covers new or changed public elements, attributes, properties, events and exports (anything that moves `api/*.api.md`), visible UI changes, bug fixes, deprecations, and Chart.js or CMS range bumps. Tests, docs, stories, CI and refactors with no visible effect don't need one.
  - Put each line under `### Added`, `### Changed`, `### Deprecated`, `### Removed`, `### Fixed` or `### Security`. Write it for a product developer: name the element or export, say what changed and what they must do, one line each. A `@deprecated` line names the replacement and the removal version.
  - `### Security`: say only that it's fixed, with no detail, and only once the fix is released (responsible disclosure).
  - Every `release-*` tag, RCs included, is a public release and goes to NuGet.org.
  - Only final versions get a section, so a release's notes list everything in it. When `release/{semver}` is cut, rename `## [Unreleased]` to `## [{semver}] - TBC` (e.g. `## [19.1.0] - TBC`) and add a new empty `## [Unreleased]` above it. Fixes made on the release branch go in that section. In the commit that sets the final version, replace `TBC` with the ISO date (`## [19.1.0] - 2026-11-04`).
  - RCs get no section of their own: an RC's release notes are its final version's section as it stands, so every RC lists everything in the coming release.
  - Every `release-*` tag gets a GitHub release with these notes once it's on NuGet.org (RCs marked pre-release). A tag with no section for its version, or an empty one, fails the build before anything is published.
- Before finishing: `npm run lint`, `npm test`, `npm run build` (commit any `api/*.api.md` change deliberately).
- Plan folders: `docs/plans/<feature-slug>/` (devkit feature-* skills). Closed plans move to `docs/archive/plans/<feature-slug>/` (feature-close); nothing outside the plans and archive folders links into a plan. Design references: `docs/design/<name>/`.
- Packages: NuGet `Umbraco.Analytics.UI`, npm `@umbraco/analytics-ui` (also the import map key) and npm `@umbraco/analytics-ui-core` (template in `Client/core/`). API reports: `api/analytics-ui.api.md` and `api/analytics-ui-core.api.md`.
- CI: Azure DevOps project "Umbraco Extensions", pipeline "Umbraco.Analytics.UI" (id 820). Service connection names in `azure-pipelines.yml` must exist in that project (NuGet: `MyGet - Nightly`, `MyGet - Pre-releases`, `NuGet (DXP)`; npm: `npm - Nightly`, `npm - Pre-releases`, `NPM`). `NuGet (DXP)` and `NPM` are the DXP team's shared connections for nuget.org and npmjs.org; the project's own `NuGet` belongs to other pipelines. Don't copy names from other products' pipelines.
- CI restores with `--locked-mode`. After any package change, refresh and commit `packages.lock.json`. Keep `Umbraco.Cms.*` mapped to nuget.org only in `NuGet.config` (MyGet copies of CMS prereleases differ and fail NU1403).
- Files CI needs must not be gitignored. The Visual Studio `.gitignore` rules hide common names like `publish/`; check `git check-ignore` when adding build scripts.
